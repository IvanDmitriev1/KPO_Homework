# Конструирование ПО | ДЗ 2 — «HSE bank»

---

### Требования
- **.NET SDK 9.0.200+**

### Сборка и запуск
```bash
dotnet build
dotnet run --project KPO_HW2.App
```

---

Поддерживаемый функционал:

- **Работа со счетами**:
  - создание, переименование, удаление счёта;
  - просмотр текущего баланса и всех операций по счёту.
- **Работа с категориями**:
  - создание, редактирование и удаление категорий;
  - разделение категорий на доходные и расходные.
- **Работа с операциями**:
  - создание операции (доход/расход) по выбранному счёту и категории;
  - редактирование суммы и описания операции;
  - удаление операции.
- **Импорт/экспорт данных**:
  - экспорт всех данных в файл выбранного формата;
  - импорт данных из файла выбранного формата.

Проект основан на принципах SOLID и GRASP и включает в себя контейнер DI.

## Паттерны GoF

### Factory Method - создание инфраструктурных объектов
**Зачем:**
- централизовать создание тяжёлых инфраструктурных объектов (подключения к БД, транзакции);
- скрыть детали создания от бизнес‑кода и команд.

**Реализация**
- `IDbContextFactory`, `SqLiteDbContextFactory`

### Proxy — кеширующие репозитории

**Зачем:**
- уменьшить число обращений к БД и ускорить сценарии чтения;
- прозрачно добавить кеш поверх существующего репозитория, не меняя клиентов.

**Реализация**
- `CachedAccountOperationRepository`, `CachedBankAccountRepository`, `CachedCategoryRepository`

### Facade - сервисы над репозиториями

**Зачем:**

- скрыть от UI сложность работы с несколькими репозиториями, транзакциями и валидацией;
- предоставить простой, предметно‑ориентированный API («создать счёт», «создать операцию», «экспортировать данные»).

**Реализация**
- `AccountOperationService`, `AccountService`, `CategoryService`

### Template method - общий алгоритм импорта/экспорта

**Зачем:**
- вынести общий «скелет» операции импорта/экспорта в одно место;

**Реализация**
- `ExportImportFormatBase`

### Visitor

**Зачем:**
- отделить логику обхода доменной модели от логики сериализации;
- позволить добавлять новые способы представления данных, не изменяя сами доменные классы.

**Реализация**
- `IDataVisitor`, `ValidationVisitor`

### Strategy
**Зачем:**
- каждый формат реализует свою стратегию сериализации/десериализации данных;
- UI позволяет выбрать нужную стратегию (формат) и передать её в `IExportImportService`.

- `IExportImportFormat`, `IExportImportService`

### Command — пользовательские сценарии

**Зачем:**
- каждый пользовательский сценарий представлен в виде отдельного объекта-команды;
- легко добавлять новые сценарии без переписывания инфраструктуры.


### Chain of Responsibility — pipeline обработки команд
**Зачем:**
- позволяет навешивать кросс‑сценарную функциональность (логирование, тайминг, обработка ошибок, валидация) без изменения самих команд;
- легко добавлять/убирать middleware, менять порядок их исполнения;

**Реализация**
- `CommandPipeline`, `ICommandMiddleware`, `LoggingMiddleware`, `TimingMiddleware`, `ErrorHandlingMiddleware`
